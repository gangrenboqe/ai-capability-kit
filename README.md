# AI 能力工具集（ai-capability-kit）

> 三个工具回答同一类问题：**怎么证明一个 AI 功能真的能用，而不是"跑起来看着像"。**

---

> **协作方式说明**：本仓库的代码由设计者与 AI 编程助手协作完成——
> 设计者负责定义需求、设定验收标准并逐项验证结果，代码由 AI 生成。
> 文中所有数字均在真机实测；凡未实测的部分均已明确标注。


## 这是什么

| 工具 | 解决什么 | 谁用得上 |
|---|---|---|
| [agent-tool-loop/](agent-tool-loop/) | 让模型不只会说话，**会调工具、会用真实结果回答**（带步数上限与失败回填） | AI 应用 / Agent 岗 |
| [local-retrieval/](local-retrieval/) | 本地知识库检索：自己分词 + SQLite FTS5 全文索引 + BM25 排序 | AI 应用 / 数据岗 |
| [prompt-eval/](prompt-eval/) | 提示词 A/B 评测：25 条用例 + 客观断言打分，**四版提示词跑出可复现的分数** | AI 应用 / 质量 / 提示词工程 |

---

## 怎么跑

```bash
# 1. Agent 工具调用循环（带离线模拟后端，评测确定性）
cd agent-tool-loop && python demo.py && python eval_selection.py

# 2. 本地检索
cd local-retrieval && python demo.py

# 3. 提示词评测（离线确定性模拟后端）
cd prompt-eval && python run.py --compare
```

**测试**（纯标准库，毫秒级）：

```bash
cd agent-tool-loop && python -m unittest discover -s tests   # 70 项
cd local-retrieval  && python -m unittest discover -s tests   # 32 项
cd prompt-eval      && python -m unittest discover -s tests   # 48 项
```

全部在 **Python 3.11 与 3.13 双版本**下验证通过。**依赖：无。**

### v4 自动回归：提示词评测已进 CI，变差自动亮红灯

```bash
cd prompt-eval
python regression.py                    # 跑 v3 全部 25 条用例，与 baseline.json 比对：好 / 持平 / 差
python regression.py --update-baseline  # 显式把本次成绩写为新基线（改基线的唯一方式）
```

- **退出码**：0 = 持平或更好；**1 = 差于基线**；2 = 基线缺失/环境错误。
- **CI**（`.github/workflows/regression.yml`）：push / PR / 每周一定时自动跑；**成绩差于基线时 job 直接变红**——不是打印个分数就完事，是门禁。
- **基线不会自动上涨**：回归检查绝不写 `baseline.json`，基线只能用 `--update-baseline` 显式更新。
  这是门禁不失效的关键——否则每次跑完自动抬基线，红灯永远不亮。
- **变差了怎么办**：输出会列出具体回退的用例和失败断言；先修回来，确属可接受的新水平再经人工确认更新基线。
- 实测演练（2026-10-14）：删掉 v3 的【简洁】守则 → 23/25、列出 N05/X04 超长 → 退出码 1；恢复后回到 25/25、退出码 0，期间基线文件一个字节没变。机制级断言见 `prompt-eval/tests/test_regression.py`。

## 迭代记录

> 这个仓库不是一次写完的。下面是真实发生过的几次「发现不对 → 改」的记录，
> 保留它们是因为：**一次失败后的归因，比十次顺利的提交更说明问题。**

### 一版提示词，改差了，又改回来

上表里 `13 → 23 → 18 → 25` 那个 **18**，是一次**真实发生的退步**：

- 第三版草稿加了一条"回答一律不超过 20 字"的硬规则，本意是治啰嗦；
- 跑分直接从 23 掉到 18——复盘发现这条规则**误伤了 6 条双关键词用例**：
  题目要求同时包含两个关键词（比如 N02 要求答案里同时有 "FTS5" 和 "bm25"），
  20 字根本装不下，模型被迫砍掉一个，判失败；
- 确认是规则问题后回退该条，改成"30 字以内 + 条件式简洁"，第四版 25/25。

**关键是：那版跑出 18 分的草稿和它的分数记录都保留了，没有删。**
"变差 → 归因 → 改回来"的完整过程留在这套工具的评测输出里，比只放一张 25/25 的截图有说服力。

### FTS5 的默认分词器不认中文：自己写了一个

`local-retrieval` 依赖 SQLite FTS5 做全文索引，但 **FTS5 内置分词器对中文基本无效**
——英文按空格切词，中文整段文字会被当成一个词，搜什么都是零结果。
这是数据库的客观行为，绕不开（除非换英文语料或换数据库）。

选择是**自己实现中文二元分词**（相邻两字成词组），接在 FTS5 前面，
然后按正常流程做召回评测——上表里 Top3 20/20 的成绩就是这套自实现分词跑出来的。
卡住的地方自己解决，而不是绕过去。

> 它会先经另一位独立 AI 助手复核，再由设计者推送发布。

## 🔴 三条我刻意写进文档的诚实边界

这一节是整个工具集**最该被先读**的部分：

1. **工具调用循环的 20/20 用的是离线模拟后端**（`ScriptedBackend`）——
   真实大模型**未实测**（当时无密钥）。**模拟成绩 ≠ 真模型成绩。**
2. **提示词评测同理**：`OfflineSimModel` 测的是"提示词守则被遵守的程度"，
   **不是真实模型的能力排名**。
3. **本地检索的速度是区间不是定值**（随机器与负载波动），
   文档里给的是**多次实测的区间**，单次精确值以 `out/eval_report.md` 为准。

> 为什么把这段放在最前面：**把"模拟跑通 20/20"写成"模型能力验证通过"，是自欺欺人。**
> 与其让人先看到成绩，不如先看到边界。

## 几个设计上花了心思的地方

**· 索引缺 FTS5 就明确报错，不静默降级。**
环境里没有编译 FTS5 扩展时，程序带着明确说明停下，而不是悄悄变成慢搜索——
**宁可明确失败，不做静默降级。**

**· 内容指纹做幂等。**
每篇文档算 SHA-256 指纹，重复导入分"插入/更新/跳过"三种结果，认内容不认文件名。

**· 提示词草稿被回退这件事写进了表格。**
`v3_draft` 得分 18 比 `v2` 的 23 低，所以被回退，README 与对比报告都写明了
**演进顺序是 v1 → v2 → v3_draft → v3**。**做错了还留着证据**，比藏起来可信。
