---

## 一、目标（一句话）

把「我调完 Prompt 感觉变好了」变成「**我能测出来好了多少**」——建立固定评测用例 + 自动打分 + 版本对比。

🎯 **这是三个项目里最能体现"工程思维"的一个。** 别人只会说"我会调 prompt"，拿得出评测集和通过率的是极少数。

---

## 二、交付物

1. `cases/` —— **25 条固定用例**（JSON 或独立文件，每条含：输入 / 期望判定）
2. `scorer.py` —— 自动打分脚本（**不许用主观打分**）
3. `prompts/` —— 至少 3 个版本的 Prompt（v1 基线 / v2 优化 / v3 回退或再优化）
4. `run.py` —— **一条命令跑完全部用例，输出通过率**
5. `README.md` —— 含对比表
6. `out/` + `SAMPLE_REPORT.md` —— 一次完整评测报告

---

## 三、25 条用例必须覆盖 4 类

| 类型 | 条数 | 例子 |
|---|---|---|
| **正常** | ~10 | 典型提问，期望回答包含关键信息 |
| **边界** | ~5 | 超长输入 / 只有一个字 / 特殊符号 / 重复问 |
| **异常** | ~5 | 问不存在的东西 / 问超出范围 / 自相矛盾的问题 |
| **对抗** | ~5 | 诱导它编造 / 越权指令 / 要求跳过规则 |

🔴 **不许挑能过的用例充数**——用例要能区分好坏 Prompt，否则这套东西自欺欺人。

---

## 四、打分规则（必须是客观断言）

| 维度 | 怎么判 |
|---|---|
| 关键词命中 | 期望包含的关键词是否出现 |
| 格式合规 | 输出是否为要求的结构（如 JSON） |
| 长度约束 | 在规定字数范围内 |
| **是否正确调用工具** | 若该用例要求调工具，调用是否正确 |

🔴 **禁止**用"质量""流畅度"这类主观描述当判据。

---

## 五、🔴 必须包含的一条记录

> **至少记录一次"改完 prompt 后指标变差，又改回来"的过程。**

理由：如果所有迭代都是一路变好，**说明用例没区分度**，这套评测就是摆设。这条记录本身就是最好的面试素材（「我改完指标掉了，又退回去」）。

---

## 六、技术约束

| # | 约束 |
|---|---|
| 1 | 零第三方依赖 |
| 2 | 禁止硬编码路径，一律 `pathlib.Path` |
| 3 | 文件读写显式 `encoding='utf-8'` |
| 4 | **同一份用例，评分标准不许因为某个版本而改**（改了要在 README 说明为什么） |
| 5 | Python 3.11 / 3.13 都要能跑 |

---

## 七、验收标准（🔴 逐条可复算）

- [ ] **1. 25 条用例齐全**，覆盖 4 类（表格列出每条属于哪类）
- [ ] **2. 一条命令跑出通过率**（如 `python run.py` → 输出 `18/25 = 72%`）
- [ ] **3. 至少 3 个 Prompt 版本**，每个都有通过率
- [ ] **4. 对比表在 README 里**（版本 / 通过率 / 改了什么）
- [ ] **5. 至少一次"变差又改回来"的记录**
- [ ] **6. 测试覆盖**：包括空用例集、全部失败、格式不合规等边界
- [ ] **7. 跨平台**：CI 在 Ubuntu + Windows 都绿

---

## 八、不做什么

- ❌ 不做人工打分（不可复算）
- ❌ 不追求用例数量到 100 条（25 条够用，关键是覆盖度和区分度）
- ❌ 不做模型微调（他明确说这条线只到 Prompt 工程）
