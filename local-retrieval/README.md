# 本地检索（local-retrieval）—— RAG 的最小可用形态

> 把历史对话/笔记变成**能查得到**的知识库：问它之前聊过什么，它能找出来、给出处。
> **零第三方依赖**（含分词库也不用，自己实现）。**依赖：无**。

---

## 快速开始（两条命令都能直接复制跑通）

```bash
python -m unittest discover -s tests    # 一条命令跑测试：32 项
python demo.py                          # 一条命令建索引 + 跑 20 条查询评测
```

输出写入 `out/eval_report.md`；想交互式查：`python -c "from search import search; print(search('data/retrieval.db', '测试'))"`

---

## 🔴 核心：中文分词是自己实现的（这个项目最值钱的部分）

**SQLite FTS5 的默认分词器对中文基本无效**：unicode61 按空格/标点切词，中文没有空格，
一整句会被当成一个词——搜「测试」匹配不到「这个测试很好」。

方案（[tokenizer.py](tokenizer.py)）：**二元切分 bigram**——

| 输入 | 切成 |
|---|---|
| 这个测试很好 | 这个 / 个测 / **测试** / 试很 / 很好 |
| 用FTS5建索引 | 用 / fts5 / 建索 / 索引 |
| 25 条用例 | 25 / 条用 / 用例 |
| 标点、emoji | 当分隔符丢弃 |

- 汉字连续段 ≥2 字 → 全部相邻二元组；单字成段 → 保留单字；英文/数字取整词转小写
- 查询侧：单个汉字自动变前缀查询（`测*`），所以搜「测」也能命中
- **实测命中**：搜「测试」→ 命中「这个测试很好，大家都满意。」（测试守着，验收标准 1）

## 检索返回什么

每次命中返回五样东西：

```json
{"doc_id": "d05_testing", "source": "d05_testing.txt", "score": 2.8342,
 "fragment": "单元 元测 [测试] 试要 要覆 覆盖 盖异 异常 常路 路径 径和 和空…", "offset": 2}
```

- **score**：FTS5 bm25 取负，越大越相关；并列时按 doc_id 稳定排序（不是随机）
- **来源位置**：doc_id + 来源文件 + 命中片段（`[]` 标出）+ 原文字符偏移

## 为什么这么做（面试一句话）

> 「我发现 SQLite FTS5 的默认分词器对中文不认字——中文没空格，整句会被当成一个词。
> 所以我在入库前自己做了二元切分，把句子拆成相邻两字词元再写进 FTS5，
> 查询侧用同样的切法拼 MATCH。搜「测试」就能命中「这个测试很好」，
> 20 条标注查询 Top3 召回 20/20，单查平均 1.4~2.1 毫秒（多次实测区间）。」

---

## 已知边界（不做什么）

- ❌ 不上向量库、不做 embedding、不做重排序模型（SPEC 边界）
- ❌ 不做增量索引：内容变了整篇重建（以 sha256 判断，没变就跳过）
- ❌ 不做同义词/纠错；OR 连接 + bm25 排序，小语料够用
- 大小写敏感问题：英文统一转小写入库与查询，中文无此问题
- 极小语料里，若某词出现在超过一半文档，bm25 的区分度会趋近 0（FTS5 会把 idf 钳到极小值），
  此时并列文档按 doc_id 稳定排序
